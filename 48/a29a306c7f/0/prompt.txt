[$grill-with-docs](/Users/atbaker/Projects/atbaker/mcpkart/.agents/skills/grill-with-docs/SKILL.md) Okay - now let's start planning out a fresh evolution of this same concept. My goal for this project: create a fun, interesting way for developers to try and learn more about the latest LLM models, via a competitive kart racing game inspired by Mario Kart.\
\
The idea is that we implement a simplified version of Mario Kart, but all the players are AI agents which control their racers via an MCP Server we ship alongside the game. Human users connect to a race and optionally give their AI agent some racing strategy instructions (e.g. "be more cautious on turns" or "always use power ups as soon as you get them"). But then the race itself unfolds without end user input - instead the AI agents control the kart via the MCP Server: steering, acceleration, breaking, use a power up - maybe even a handbrake. The race should probably have 3 laps and end users can watch it via a web UI (or maybe via an MCP App / a Codex Plugin / a Claude Code "mod"? Not sure which approach is best). Users authenticate via a GitHub OAuth app, so their racer name is their GitHub username. Later on we might add the ability to be part of a racing "team" via the user's GitHub organizations. Users can join races via a lightweight matchmaking system to connect them with other live racers, or just race against bots / have live races get padded out with bots (I'm undecided if we should do 6 or 8 racers per race). For the "bot" racers, we just run those ourselves using maybe Pi or OpenCode or a similar OSS harness. We'll have public leaderboards which show the winningest racers and also, ideally, the winningest models and/or MCP clients (e.g. Claude Code vs. Codex).\
\
I work for Temporal and am doing this project for work, so we should also make it a showcase of how well Temporal works with AI agents and MCP. I'm thinking that could happen in a few ways: maybe the race itself is a Temporal Workflow (if we can get it to be performant enough to support a realtime race - might have to use local Activities or something). If that's not possible, then at least using Temporal to power most other parts of the platform should be sufficient: the MCP server, our orchestration for each race, the matchmaking, etc.\
\
When I tried building this back in December, the models were too slow. Where this project could get really interesting is if it can illuminate the pareto frontier between performance and intelligence. In theory, the winningest models will need to be sufficiently low latency and also sufficiently smart to outwit the other racers. In December, even the most lightweight models were still too slow to keep the racers on the race track. Even when I compromised on the vision and basically made it a turn-based race with one second ticks instead of a realtime race, it still didn't work. But today, with Jev, Clef, and this new generation of System One models, I think there's a chance this concept could be viable.\
\
When we get to prod, we'll want to deploy it on GCP using Temporal Serverless Workers. But to start, I really just want to try rearchitecting and rebuilding this concept here in my dev environment to see if it's even viable. Do Jev, Clef, and the new OpenAI Decisions API respond fast enough in order to sufficiently control a realtime kart racer?\
\
A few other topics on my mind as we get started:\
\- The previous implementation of this project used Python, which is my preferred stack. But I wonder if Rust might be better for powering the race itself, now that we're aiming to do it in realtime instead of via one-second ticks?\
&#x20; \- My guess is we might have a couple different production services anyway, so using different stacks for each isn't a huge deal. We could use Rust for running the game itself and Python and FastMCP for the MCP server\
\- The visuals in the previous evolution in December were a bit dry. If our racing game is really viable, I might be interested in aiming for a 3D low polygon art style for the game UI. But for now, let's just stick with a 2D SVG-based UI you implement yourself\
\- Which brings me to how human users will experience the UI: we can of course provide their AI agent a spectator URL as part of our MCP server responses and tell the user to open the link in their own browser. But ideally, the user would be able to watch the match inside their chat window for their AI agent of choice. MCP Apps in theory should help with this? But I know the spec is unevenly adopted. Maybe Codex and Claude Code have their own plugin APIs for this? We should research our options\
\- As for the game mechanics: in the previous tick-based system we descoped a lot of things that make a kart game interesting (like collisions). I'd rather start this new exploration with the assumption that we can support a realtime kart game experience and thus create a higher fidelity version of a kart game. It doesn't need to be nearly as fancy as bona fide Mario Kart. But I'd want it to have realtime gameplay, collisions between racers (so some real-ish physics), a few power ups, etc.\
\
Feel free to ask me lots of questions as you plan. Also feel free to run some experiments. You can use the Codex CLI with the OpenAI Decisions API to test things out as you go along. And use Exa for research tasks liberally. Document our plan as go along.

---

And remember, for this first PoC, what I really care about is validating whether a realtime kart game is even possible using these latest decision models, starting with the OpenAI Decisions API
